# Webhooks and idempotency

Status: current.

## API idempotency

Money-moving endpoints require `Idempotency-Key`. The row key is `(merchant, operation, key)`. The request body is canonicalized and SHA-256 hashed. A first caller inserts `IN_PROGRESS` and performs the local mutation in the same transaction. PostgreSQL's unique constraint chooses the winner when concurrent requests race. A loser reads the committed row: same hash replays the stored status/body; a different hash returns `422`; an in-flight record returns `409`.

Keys are durable and have no automatic short TTL because retries and dead-letter replay can outlive a cache window. Redis is never used as the idempotency authority.

## Webhook inbox

The Stripe receiver preserves the raw request body and uses the official SDK's `constructEvent` verification with `STRIPE_WEBHOOK_SECRET` before insertion. It normalizes supported Stripe objects, stores the normalized payload, headers, receipt time, and external event ID before returning `202`. Duplicates conflict on `(provider, provider event ID)` and return the original inbox ID.

Workers claim pending events with `FOR UPDATE SKIP LOCKED`, set a processing lease, and dispatch by event type. Capture completion checks the successful-attempt guard and unique ledger business reference. Unsupported event types are retained as `IGNORED`. Missing payment/attempt/correlation prerequisites retry with bounded backoff; domain errors such as invalid transitions go to `DEAD`. This is not a guarantee for every out-of-order event or stale-worker interleaving; see [failure recovery](failure-recovery.md).

At-least-once delivery is assumed. Exactly-once delivery is not.

New confirmed captures commit a journal-backed accounting lot with the existing financial effects and inbox PROCESSED mark. The merchant/currency advisory lock is acquired before provider-mirror writes, then scope, payment and CAPTURE attempt locks serialize application. The successful-attempt guard, unique ledger business reference and unique lot attempt/journal references prevent repeated effects. Lot creation errors abort the whole business transaction; the existing inbox failure path records RETRY or DEAD separately. Original provider references and command keys are preserved. Authorization, synchronous provider responses and unknown command outcomes create no lots. Historical successful attempts are not backfilled on replay. [B2.1](audits/h1-fix-02-b2-1-capture-integration.md) records PostgreSQL evidence.

[B2.2](audits/h1-fix-02-b2-2-refund-integration.md) adds ACCOUNTING_EXCEPTION to the schema and a disconnected refund service that locks the actual inbox UUID, then atomically commits either financial application plus PROCESSED or an OPEN exception plus ACCOUNTING_EXCEPTION. Original payload and references remain immutable; exception events are excluded from ordinary claiming. Direct service-path PostgreSQL tests exercise this disposition. The live processor still calls legacy refund handling and writes its existing disposition: future dispatch must pass the locked inbox identity, preserve the service's returned disposition and acquire admission before mirror mutation. Operational errors must retain the existing bounded retry/DEAD policy; unknown ownership must not be guessed. No runtime exception routing or human resolution/requeue workflow is activated here.

[B2.3](audits/h1-fix-02-b2-3-dispute-integration.md) follows that transaction/disposition contract for the disconnected dispute path. It validates normalized object identity, original ownership/amount and capture/mirror provider relationships before financial replay. Coherent repeated open after close acknowledges old evidence without reopening; contradictory outcomes retain review evidence. B2.3.1 validates trusted close identity before a missing-open RetryableWebhookError, ahead of history/workflow admission, so a later pending capture alone cannot create a terminal exception. Existing cases still require frozen financial evidence and applicable workflow checks. Service-level PostgreSQL tests preserve the RETRY inbox without effects; future dispatch must execute the existing bounded prerequisite process. A normal rejection commits exception evidence; an operational abort rolls back exception/disposition too and retries the separately persisted inbox. The current signed receiver/legacy processor is unchanged.

[B2.4's dormant settlement service](audits/h1-fix-02-b2-4-settlement-integration.md) refuses pending generation/completion when known correlated STRIPE refund-success/dispute-open/close evidence remains PENDING/PROCESSING/RETRY/DEAD. It raises ACCOUNTING_PREREQUISITE_PENDING instead of hiding that evidence in a zero-effect result; a future caller must classify it for retry after application/reconciliation. This is a locked financial-state check with a current inbox read, not a receipt-arrival barrier or unknown-reference discovery guarantee. Full signed dispatch, claims/backoff, new-receipt admission and old-worker drain remain B3 work. Completed settlement replay checks immutable historical evidence and changes no inbox, journal or audit.
