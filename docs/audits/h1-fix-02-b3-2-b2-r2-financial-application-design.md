## 3. D02 evidence gap inventory

The actual command lifecycle is API idempotency TX → accepted attempt/refund + outbox + audit + replay response → relay lease/confirm/mark → RabbitMQ delivery → adapter call → returned result → mirror/child TX → ACK. Redelivery may repeat any remote call using its original provider key.

| Gap | Missing or mutable authority | Required smallest correction |
| --- | --- | --- |
| Command identity | Handler trusts envelope aggregate/payload without a full stored-outbox/accepted-child comparison. Outbox payload and accepted identity have no general immutable command-era guard | Freeze and validate accepted operation, owner, amount/currency, account context, policy and provider key for future compatible commands; keep operational outbox lease fields mutable |
| Account | Port has no provider-account/mode context. Mirror uniqueness is provider/key, not account/object ownership | Server-owned endpoint/account and test/live identity on every new observation; validate signed/returned account context where present; never infer account from metadata |
| Result | Mirror `ON CONFLICT` replaces object, PI/Charge, status and raw_response; raw_response is only adapter metadata | Retain each genuine response as immutable source before any mirror update; contradictory responses append review rather than overwrite authority |
| Amount | Mirror amount/currency are copied from input, not returned provider facts. PI may represent several captures | Preserve request and actual provider fields separately; never turn requested gross or cumulative PI amount into an observed per-capture success without an attributable witness |
| Bytes and request ID | Adapter discards the SDK object/HTTP context. JSON serialization of a parsed object cannot recover original bytes | Capture response-body bytes at transport consumption, with completeness, status, selected headers/request ID and SDK/API/normalizer version |
| Failure/unknown | Exceptions become retry/DLQ reasons; no durable remote-attempt/result lineage. No-object outcomes cannot fit 0006's required object ID | A pre-call immutable execution identity plus immutable outcome envelope allowing no object/body, with explicit unknown/error classification |
| Replay | Same command/key may yield cached/retried responses or crash after success; mirror retains latest only | Separate accepted command, local invocation and received observation identities; identical publication is idempotent, changed evidence is retained |
| Reconciliation | `fetchStatus`/issue snapshots are lossy/current and not immutable COMMAND_RESULT | Trusted PROVIDER_LOOKUP source with query target/account/request/version/run lineage. Never relabel a lookup as an original command response |
| Admission | No result obligation or revision change before callback | Publish confirmed relevant observation + its obligation/review/revisions atomically; pending/unknown alone remains Option A neutral |
| Projection | Observation snapshot is not independently derived from retained wire data; no genuine restricted publisher exists | Restricted attesting producer plus SQL structural projection; SQL validates lineage/normalization, not TLS or Stripe HMAC for API responses |
| History | Current mirrors, ACKs and stored request payloads cannot recover lost provider responses | No migration/backfill fabricates D02. Missing history stays D03/ineligible; a new lookup records only what was actually queried now |

The installed Stripe RequestSender was inspected: its JSON response path calls `toJSON()` and attaches a non-enumerable `lastResponse` transport object. Neither that attachment nor response-event parsed JSON proves that original body bytes are available after consumption. D02 must demonstrate a supported, bounded transport-body capture against the pinned SDK; do not assume `JSON.stringify(result)` or `lastResponse` supplies those bytes. No private SDK patch is selected by this design.

## 4. Proposed provider observation and publisher contract

### 4.1 Minimum durable structures and source identity

Reuse `provider_financial_observations` as R1's owned object witness, not a new generic event bus. Two narrow companion concepts are needed because an object observation cannot represent a call that returned no object:

| Proposed forward contract | Required data / constraint |
| --- | --- |
| Immutable `provider_command_executions` | One local invocation ID prepared before the call; provider/account/mode, outbox UUID, accepted operation kind/UUID, payment/merchant/currency, canonical key, exact command snapshot/hash, request method/path/API version and non-secret request parameters, recorded accounting policy/acceptance epoch. Composite ownership and operation-shape checks; unique invocation ID. The original key is deliberately **not unique per invocation** |
| Immutable `provider_observation_sources` | Typed COMMAND_RESULT execution FK **or** PROVIDER_LOOKUP query identity; stable observation key; RETURNED_OBJECT / RETURNED_ERROR / UNKNOWN_OUTCOME; original body bytes when received, complete/partial/absent marker, hash, HTTP status/request ID/selected safe headers, actual parsed result/error facts, transport failure category and normalizer/publisher version, observed/retained times and database principal. Lookup identity includes configured account, requested object kind/ID, query parameters/time and reconciliation run/actor; it cannot claim an original execution. Absence of bytes/object is explicit, never synthesized. Unique source-kind/source key; exact replay compares the entire immutable fingerprint |
| Existing object observations, new protected source reference | A new-format COMMAND_RESULT must reference its owned outcome/execution; SQL derives accepted owner/key/amount and actual object/PI/Charge/status from retained sources. Keep accepted amount distinct from actual returned amount/cumulative fields in the source envelope. Existing snapshots remain immutable, without newly invented trust |
| D02 admission records | One source obligation per financially relevant outcome, with immutable source identity and guarded mutable disposition/revision. Same account/scope authority and monotonic revision writer as receipts. An object-bearing projection cannot commit without its required obligation; no-object errors retain invocation lineage too |
| Evidence/application links | Typed FKs connecting outcome/object observation, actual R1 receipt/proof and canonical application or verified no-effect. A receipt link cannot change either source's authenticity or replace original evidence |

Accepted command financial fields and future execution ownership must be protected prospectively in forward SQL/privileges. Compare broker ID, event type, aggregate ID and every financial field with the stored outbox and accepted attempt/refund **before** the call. Validate child kind and canonical `capture:<attempt>` / `refund:<refund>` key; authorization/void retain their existing stable keys. Record immutable command policy through acceptance; do not take policy from a broker field or reinterpret an old command under today's scope. The existing outbox publication/claim fields remain separate delivery state.

Only capture/refund object results need to feed R1's current COMMAND_RESULT witness allowlist. Authorization and void executions still need accountable request/outcome lineage and compatible workflow handling, but do not invent capture lots or broaden 0006's object-kind checks by labeling them CAPTURE. Disputes have no accepted command in this platform. The current global dispute-ID uniqueness also limits multi-account reuse of a `dp_` identity: retain that conservative refusal unless a separate reviewed ownership migration makes it account-qualified. Do not claim new multi-account runtime support.

Lookup publication uses the same immutable source-envelope protections and admission transaction, with its own typed query lineage and raw-body normalization. It may corroborate current state or block on drift, but cannot satisfy a builder predicate that specifically requires COMMAND_RESULT. In particular, a new lookup cannot recreate lost historical capture-command evidence or turn a refund object into an owned accepted refund solely through a shared PI. Reconciliation issue/run rows link to the immutable lookup source; changing their note/status changes no source authority.

### 4.2 Publisher sequence and outcome meaning

1. Fresh local TX validates the accepted command and server account, records immutable execution/request identity, and commits before calling Stripe. A prepared row means **may have been sent**, not proof it was sent. A crash between prepare and send therefore recovers conservatively with the same key.
2. Call outside database locks. Capture complete original response bytes at the adapter/transport boundary, preserve actual response facts, and normalize under a versioned allowlist. Never retain authorization secrets or generic request headers; exact response evidence stays private like R1 receipts. If bytes contain sensitive provider fields, apply protected storage/access rules without silently rewriting the claimed original.
3. A restricted publication TX takes account authority, then known A/S where ownership is trusted, validates execution/accepted identity and SQL normalization, appends outcome/object projection plus required obligation/review/revision. Initial D02 intake can conservatively choose account UPDATE before scope so unexpected response ambiguity never requires a SHARE upgrade; later optimization needs its own ordering evidence. Retain truthful response bytes even when their meaning contradicts the accepted command: create review/obligation with no authoritative object projection, rather than discard the source through semantic validation failure. A conflict with another immutable owner keeps account-level ambiguity or the proven scope blocked, without acquiring that other owner's arbitrary scope. Mirror synchronization is a separate subordinate concern and cannot make the source true. Prefer committing immutable intake first, then a compatible guarded mirror TX, so a mirror failure cannot erase retained evidence. ACK only after required durable publication and bookkeeping succeed; replay reuses the same invocation/observation when recovering a local publish failure.
4. On a new broker redelivery that really invokes Stripe again, allocate a new local execution ID but retain the **same provider key and accepted operation**. Capture any additional response separately. A repeated publication of one response returns the same row. A changed response cannot overwrite that row or disappear behind `ON CONFLICT DO NOTHING`: retain a separate conflicting witness and blocker, with original source key/fingerprint linked.
5. If local publication fails after provider success, retry publication with the copied evidence while available. Process loss leaves a prepared execution with unknown outcome; recover via same-key retry or a truthful new lookup outside locks. Do not fabricate the lost body or release reservations. No design can atomically persist every remote fact across a crash before local retention.

| Observation | Meaning and admission |
| --- | --- |
| HTTP request succeeds, object still pending/requires_action | Transport success is not financial success. Retain object/witness, track confirmation, preserve gross reservation and Option A neutrality |
| Confirmed attributable capture/refund result | Durable blocking obligation before a webhook, even if local application is delayed. It supplies correlation provenance and admission evidence, not a signed event or automatic journal |
| Returned definite failure/cancellation | Retain exact error/object and validate terminal meaning. Only an owned, supported definitive no-effect proof may later release capacity; PermanentProviderError or a 4xx class alone is insufficient |
| Timeout/disconnect/incomplete response/5xx | UNKNOWN or retryable observation as justified by actual facts; no invented terminal failure or no-effect. Preserve provider key and reservation. A raw status/code is not a money oracle |
| Same object pending → confirmed | New chronological observation, not automatically a contradiction. Terminal conflict, changed owner/object/principal/currency or incompatible source is blocking review |
| Late pending after a completed operation | Retain it, do not regress the operation or its financial totals. Verify supersession against immutable completion; a genuine contradiction still blocks separately |
| Lookup reports missing object | Retain lookup target/request/error; missing now does not prove a previous request never executed. No automatic reservation release |

Initial R2 financial application remains **signed-receipt driven**. D02 results/lookups can establish ownership, block admission and corroborate a later signed proof; they cannot directly invoke refund/capture financial writers. A result-only financial application/timeout release is outside this automatic contract and requires separately reviewed operation-specific provenance. This preserves D01's “no fabricated inbox” boundary while providing durable recovery instead of assuming a callback always arrives.

Stripe documents parameter comparison and replay behavior for [idempotent requests](https://docs.stripe.com/api/idempotent_requests); provider retention is not indefinite local authority. Never generate a replacement key to escape an unknown outcome or blindly resend an old key after its safe provider replay horizon. Hold for reviewed lookup/reconciliation when execution cannot safely be established. Signed callbacks remain a separate [webhook authentication/delivery boundary](https://docs.stripe.com/webhooks).

### 4.3 Trusted SQL, privileges and R1 integration

The D02 producer receives a separate explicit restricted authenticated LOGIN pool and narrow publication EXECUTE capability, without receipt-publication EXECUTE, proof writes, financial writes, owner membership, schema CREATE or broad inherited rights. A narrowly privileged NOLOGIN function owner may append D02 sources/obligations and guarded revisions, but cannot post ledger entries or change original R1 evidence. Reuse the admission owner for monotonic revision updates through a narrow routine; do not grant D02 direct revision UPDATE, which 0007 correctly rejects for other principals. Audit actual table **and column** privileges/default grants. No production roles or credentials are created by this design.

Publisher routines pin `pg_catalog,pg_temp`, qualify persistent tables and revoke PUBLIC EXECUTE. Ordinary workers cannot assert trusted source flags, insert projection rows or bypass mandatory obligations. SQL checks raw-body parsing, exact integral amounts, object/type/status/reference/account shape, accepted command equality and complete fingerprint; remote TLS identity and truthful capture of bytes remain trusted adapter assumptions, exercised with authenticated mock transport tests. SELECT needed to validate owned source/journals is distinct from ledger write authority.

Keep 0006's fixed proof revision1 and frozen source IDs readable. New envelope validation must not rerun historical proofs against newly fabricated provenance. Add an explicit source-contract format for prospective projections, with no caller-created historical stamp/downgrade. `load_effective_financial_evidence` continues to return the same original sealed interpretation; current conflicting observations are a **separate live admission check**. A new observation invalidates the relevant certificate/revision without retargeting an old proof.

For refund events lacking refund metadata, the exact same-account/object COMMAND_RESULT witness identifies the accepted refund. It must still reconcile to frozen lots and genuine capture observations. For disputes, capture-command provenance supplies uniquely owned PI/Charge, not a fabricated dispute request. Later signed receipt, its proof and D02 source can share an application acknowledgement only after exact account/object/operation/principal/owner checks. Pending D02 source → terminal signed event links record real lifecycle progression; they do not falsely claim the earlier response was signed or terminal.

## 5. Financial application transaction model

### 5.1 Canonical application and its evidence

Propose a small immutable `financial_applications` relation with operation-specific typed references, not a second ledger. Its identity is `(operation family, accepted operation UUID or owned dispute/batch UUID, phase, currency)`. Refund success/failure share one terminal slot; capture success/failure share one terminal slot; dispute OPEN and CLOSE have separate slots, with exactly one close outcome. Provider account/object identity is checked against that operation, not used to create a second application key for the same internal obligation.

An application records policy/acceptance identity, applying scope/epoch/revisions, exact proof kind/inbox/revision, immutable calculation inputs and per-lot source state, all main/hold journals and allocations/items, final workflow facts, immutable financial audit reference, and POSTED / ZERO_EFFECT / VERIFIED_NO_EFFECT result. Journal/reference children use composite ownership FKs and complete-group checks. Source acknowledgements for additional observations/duplicate events reference this canonical application; they never replace its first applying inbox/proof.

Use typed proof alternatives: refund/dispute uses 0006's owned proof tuple; capture uses the pre-lot capture proof described below; internal settlement/payout uses owned internal command/candidate/reservation evidence with **no pretend webhook**. Explicit CHECK/trigger logic requires exactly the applicable alternative; nullable composite FKs alone are insufficient. No monetary source or service-supplied calculation object is accepted merely because it has a TypeScript type.

Capture needs an immutable `payment_operation_evidence` companion and shared SQL reader for pre-lot payment-attempt outcomes. Its capture-success shape binds original signed receipt, configured account, accepted CAPTURE attempt/outbox/key, exact confirmed gross/currency and owned PI/Charge/D02 execution. It **does not require the journal/lot it is about to authorize**. Both capture service and immediate/deferred SQL consume this same reader; do not add a second application-only interpretation. Extend receipt classification/owned-obligation references through typed attempt-proof FKs, preserving existing refund/dispute proof1. Current 0007 classifies payment-intent events conservatively as unclassified: retaining a capture receipt in R1 is not capture-proof support.

The same companion has explicitly disjoint capture-failure, authorization and void shapes, each tied to its own accepted attempt/command/key and authenticated signed event. Authorization amount comes from actual provider authorization facts; void's accepted zero amount is permitted only in that workflow-only shape. Failure must be attributable to the correct operation and consistent with any prior success. Those shapes create no capture lot or financial journal, but require their own immutable workflow/audit/no-effect disposition and automatic-capture outbox linkage where authorization emits one. They use D02 execution/source envelopes without relabeling them CAPTURE object observations. Missing or ambiguous operation attribution remains blocking review, not a generic no-journal clearance. The attempt-proof reader and receipt classifier must implement and test this complete allowlist together in R2-B.

The normalizer currently uses PI metadata `captureAmount` and `captureAttemptId`; metadata plus `intent.status` is insufficient proof of attributable captured principal, especially for partial captures sharing a PI. Capture sealing must compare the accepted request and complete genuine command response with authoritative provider capture/cumulative facts and previously recognized captures. Require an unambiguous operation-specific amount witness; a cumulative snapshot that cannot isolate this capture remains blocking review. Preserve shared-PI captures without asserting PI uniqueness per capture, and never treat `requires_capture` alone as proof of this operation's success. Pin and test the provider interpretation before implementing that branch; unsupported external multicapture stays excluded.

### 5.2 One caller transaction, one complete result

The dispatcher owns the transaction; services receive the same `DbTransaction`, operation-private claim, transaction-local SQL-validated permit and exact proof selector. Do not nest service transactions or invoke the existing self-locking sealer/resolver after the financial suffix. Split self-locking entry points from a checked locked core, with the latter unreachable without a database-validated current permit. A caller-provided JSON token/session GUC is not sufficient authority.

The permit binds transaction/backend, private source/claim generation, scope, stored policy, acceptance identity, allowed action/recovery kind, current epoch and evidence revisions; it cannot survive commit, be reused by another operation or authorize a second scope. At the compatible restricted writer boundary, direct new-era effect/workflow writes must be rejected without such checked authority.

A concrete candidate is a protected permit relation keyed by server-derived `(pg_current_xact_id(), pg_backend_pid())`, allowing one operation per application transaction. A restricted SQL issuer owns/revalidates the private wrapper and authority prefix, derives every stored permission field from protected rows, and inserts the permit; the worker has no direct INSERT/UPDATE/DELETE or owner membership. Immediate/deferred financial guards look up the **current** transaction's row and compare exact operation/proof/action/claim/policy, rather than accepting a caller's permit UUID. The source/effect manifest records authority revisions before and after guarded writes; the deferred check validates those changes and the final blocker set, rather than incorrectly requiring the pre-write revision to remain unchanged after its own effect. The guarded issuer/recovery entry points are distinct from current self-locking R0 helpers. Retained permit rows from committed transactions confer no later authority; financial application/effect records remain the audit truth. PostgreSQL17 supplies the full [transaction identity function](https://www.postgresql.org/docs/17/functions-info.html), including top-level identity across subtransactions. Test savepoint rollback, cross-transaction/backend reuse and forged ordinary-role writes. Exact keys, grants and function composition remain R2-A DDL review items; this candidate is not installed machinery.

Before the first financial mutation, a guarded SQL preparation routine acquires the ordered operation parents/lots/allocations and derives a protected, immutable calculation/source manifest under that permit. The service consumes it and the commit validator compares actual rows/entries with it. A caller-supplied “before” snapshot cannot authorize pending-versus-available or PSP-versus-cash selection. Direct new-era monetary/workflow writes require this prepared manifest; a worker cannot first alter the source state and then ask SQL to certify the altered snapshot. Journal guards map every permitted business type/ID to its root operation and complete effect set, rejecting arbitrary business-type or omitted-era bypasses. This is a narrow extension of the existing SQL validation boundary, not a second source of balances.

An authorization root may emit the existing automatic-capture subintent only as a specifically validated child in that root's manifest: exact derived attempt, same scope/recorded policy, stable key, outbox and audit, committed with the authorization disposition. It cannot authorize an unrelated second financial application. Accepted-obligation recovery must explicitly account for this child under its recorded authorization contract; PAUSED/DRAINING is not an excuse to drop it or create arbitrary new spending.

1. Lock this operation's inbox/idempotency/internal-outbox wrapper first. Compare claim generation, identity and expected status; a short claim transaction has already ended. Discover ownership tentatively without locks.
2. Choose account lock mode before scope; acquire account authority → canonical merchant/currency advisory → scope. Re-read policy/mode/epoch, source obligations and all relevant conflicting evidence in fresh READ COMMITTED statements. Settlement/payout/new-intent permits require clean admission. **Application permits differ:** they may consume their exact AWAITING_APPLICATION obligation; a blanket call to `inspect_receipt_admission` would block on the worker's own source forever.
3. A normal application permit validates its proof, owned accepted obligation and compatible history. Unrelated unresolved evidence/OPEN exceptions cannot be ignored; use a separately reviewed, exact-source recovery permit or defer. No “ignore this scope's blockers” flag. In PAUSED/DRAINING, intake continues; accepted obligations may apply only through this checked recovery contract under recorded policy, never through new-intent/spending permission.
4. Acquire shared header if applicable, all payments NKU, child parents, validated mirror locks if needed, lots/allocations/items in §8 order. Read proof through the shared SQL reader; revalidate identity/principal/terminal state and current source/hold calculations. Look for an already completed canonical application before any financial delta.
5. Construct hold-adjustment journals in stable cause/allocation order, then the main journal, omitting zero lines. Apply the complete allocation group, workflow totals/status, application/effect manifest and one financial audit. Reread the actual persisted final group for SQL validation.
6. In the **same TX**, create verified source dispositions/resolution links, conditionally finalize this inbox/internal outbox at its current claim generation, and advance guarded scope/evidence revisions. All D02 obligations already linked to this operation/outcome must either be proven covered and discharged or remain explicitly blocking; they cannot disappear on a broad PI match.
7. Deferred validators run on both sides of the relationship at COMMIT: no final application without exact effects/state/audit/disposition, and no new-era journal/allocation/workflow finalization without its complete application. Only successful COMMIT returns APPLIED / VERIFIED_NO_EFFECT / VERIFIED_DUPLICATE. REVIEW_REQUIRED commits evidence/blocker and no financial effect; RETRY retains the obligation. ACK follows commit.

Late SQL failure rolls back the entire financial TX. A separate generation-conditional failure/review TX may record the refusal afterward; it cannot retain partial money and mark PROCESSED. A connection error at COMMIT is ambiguous: recover by canonical identity and revalidate committed evidence, rather than assuming rollback and issuing a new financial operation.

### 5.3 Protected financial era and dormant compatibility

Current version0/NULL gates are a closed foundation, not a usable historical stamp. The final forward enforcement package must protect the historical set, default future evidence to the new contract, deny caller-created version0/NULL/downgrade bypasses and require proof before RESERVED/PLANNED/OPEN history makes any new financial effect. Preserve original finalized version0 bytes/IDs/checks; unsupported histories remain ineligible. New proof does not rewrite historical attribution or grant activation.

**Do not install final default1 enforcement independently while current payload-only writers remain live.** R2 can be independently committed as dormant source/forward-DDL artifacts tested in disposable databases, while production installation stays a coordinated maintenance/floor gate. Additive-only storage checkpoints may be compatible with the current runtime; opening financial references and changing defaults are not automatically compatible. The eventual installation must provide every compatible adapter and explicitly refuse unsupported legacy work; it must not run old payload-only finalizers against new-era constraints. No intermediate deployment is authorized by the checkpoint sequence.

Tests distinguish baseline legacy behavior on 0000–0008 from proposed enforced-floor behavior in separate disposable installations. Preserve financial assertions; do not make incompatible new writes “pass” by weakening proof/default guards. Synthetic dormant admission can test financial calculations, as earlier suites do, but is not evidence for real policy/claim permits; permit/ordinary-role rejection requires its own actual SQL tests. Migration defaults create zero active scopes and no certificate. No production test-mode flag or credential fallback is proposed.

## 7. Exactly-once financial effect and ledger invariants

Delivery remains at least once. Stable provider keys reduce duplicate external execution within the provider's contract; PostgreSQL owns uniqueness of committed internal effects. There is no exactly-once delivery claim.

## 8. Combined lock graph and concurrency matrix

The installed serialization row for provider-account intake is **`financial_evidence_accounts`**. `receipt_intake_authority` stores its guarded revision; it is not a replacement first-lock authority. R1 original/seal/bind uses account UPDATE before scope, while staged readers use SHARE. Preserve this distinction instead of introducing a second independent account lock.

Proposed common order, retaining the accepted private-wrapper exception:

```text
one private inbox / API idempotency / claimed internal-outbox wrapper
  → provider account row(s), chosen SHARE or UPDATE before scope
  → canonical pg_advisory_xact_lock(hashtextextended(merchant_uuid_text + ':' + currency,0))
  → accounting scope (policy/mode/epoch/evidence, NKU for non-key mutation)
  → existing settlement header, if completing (or own payout row for payout path)
  → ALL affected payments by UUID, NO KEY UPDATE
  → attempts by UUID (all touched kinds) → refunds by UUID → disputes by UUID
  → validated owned mirrors, if updating, in stable key order
  → lots by capture-attempt UUID
  → dispute allocations by lot/UUID → refund allocations by lot/UUID → settlement items
  → immutable source/binding/proof reads; new private application/journals/accounts/entries
  → full effect/state/audit/source disposition and conditional inbox/outbox finalization
  → deferred validation and COMMIT
```

The existing B.1 sealer takes scope FOR UPDATE, not NKU. It stays a separate fresh transaction; invoking it after account SHARE/A/S would introduce an upgrade/reverse-prefix risk. Proof reads never UPDATE an immutable proof to obtain a lock. Binding/unknown-barrier recovery chooses exclusive account mode at entry. If discovery needs a different scope or stronger intake mode, roll back and start a separately classified attempt. Do not acquire another worker's inbox, another request's idempotency row or an existing settlement header after the financial suffix.

R0.2's deliberate cross-account conflict publication is the narrow exception: it owns one inbox, sorts **all** implicated accounts before any scope, then its derived scopes in canonical order. It does not post money. Recovery of its barrier set follows that complete ordered authority set, never an arbitrary second-scope financial application. Ordinary financial application remains one scope. D02 publishers mutate source obligations only under account/A/S; they do not lock a shared outbox lease row before later financial locks or make application acquire another command's private wrapper after scope. Immutable source FKs/readers are distinct from a blocking FOR UPDATE on another inbox.

New private generation headers/lots/journals are not shared-header inversions. Existing triggers revisit already prelocked parents: allocation writes update refund/dispute and lot; hold effects lock OPEN allocation; item writes version batch; settlement checks revisit scope. Include FK KEY SHARE, unique/speculative insert waits and actual row-version UPDATE effects in the graph. Payment NKU is necessary for the accepted capture/generation FK compatibility. Shared platform account creation across merchants is outside scope serialization; preserve the cold-account schedule and require a minimal common account-order correction if a real cycle is reproduced.

PostgreSQL17 documents [row/advisory lock conflicts and transaction lifetime](https://www.postgresql.org/docs/17/explicit-locking.html) and [READ COMMITTED statement snapshots](https://www.postgresql.org/docs/17/transaction-iso.html). Those support the lock interpretation; the schedules below are **planned**, not executed evidence or a deadlock-freedom claim.

Use baseline capture 10000 / fee 300 / net 9700 and refund 5000 / fee 150 unless stated. Every schedule must gate actual SQL, identify distinct backend PIDs, observe `pg_blocking_pids`, use bounded waits, release in finally, await all participants, and assert exact committed accounts/references/revisions. Do not retry a 40P01 into a “successful schedule.”

## 9. Exception, failure and recovery policy

| Failure or state | Durable recovery / review requirement |
| --- | --- |
| Provider success, local result publication rolls back | Prepared invocation and original command/key survive. Republish copied truthful response if still held; otherwise recover using same-key safe replay or a new explicitly sourced lookup. No fabricated response bytes, success journal or changed key |
| Command may have been sent, result unknown | Retain reservation/accepted identity, retry/reconcile outside locks within safe provider limits; mark unknown, not failed. It excludes activation of that history but alone does not introduce a pending-refund payout hold |
| Receipt admitted, correlation unavailable | Retain exact original/account obligation and durable retry dependency. Trusted D02 arrival may enable fresh sealer/binder transactions; bounded retries eventually escalate under H04 owner/deadline, never timeout-clear |
| Proof sealed, binding/application fails | Original blocker survives; committed proof remains fixed. Retry same proof/revision after current claim/admission validation. No proof replacement or speculative attribution |
| Financial SQL fails after first journal/allocation/hold write | Entire TX rolls back main/adjustment journals, application, allocations, state, audit, source dispositions and revision increments. Original independently retained receipt/proof remains. Record failure only after rollback under current claim |
| Journal committed, ACK/HTTP response interrupted | Recover by canonical application and source identity; verify exact journal/effect/state/audit/disposition then ACK/return saved result. Never post again or alter first-applied evidence. A journal without the complete application is integrity review, not successful replay |
| Worker crash before/after COMMIT | Before: no local partial effect. After: durable canonical result wins. Ambiguous COMMIT response requires read/revalidation. Claims can be reclaimed, but old-generation application/failure bookkeeping must refuse |
| Late contradictory response/receipt | Retain new immutable witness and independent blocker/review; preserve original proof/journals/allocations and accepted payout liability. No monetary rollback or automatic compensation. Cleared original resolution cannot absorb a new cause |

| Stale scope/intake evidence revision or policy epoch | Abort permission/certificate use; reacquire/revalidate from fresh authoritative statements. Same accepted operation retains its stored accounting policy. No fallback to legacy, revision reset or reuse of stale certificate |
| Unsupported candidate/legacy history or numeric bound | Durable RETRYABLE / BLOCKING_REVIEW / TERMINAL_UNSUPPORTED classification, immutable ownership retained. Pre-admit bounded new batches, recheck completion. Existing oversized/misowned candidates are not silently rewritten/superseded |
| Overlap / unknown provider net loss | Human-reviewed reconciliation with actual source/effect accounting. Preserve all evidence/reservations, explain any approved compensating journals in a separate repair plan. This design deliberately supplies no automatic monetary oracle |

H04 requires an assigned operator, tracked review deadline and escalation before operational reliance on a broad account barrier. The concrete person/deadline belongs to an environment runbook, not an invented timeout in SQL. Reconciliation issue notes are useful review records but never release financial capacity or authorize resume. General refund collection, payout cancellation, external bank recovery and automatic monetary compensation remain outside scope.

## 10. Receipt-to-application lifecycle and admission clearance

The normal chain is **verified receipt → mandatory admission obligation → trusted fixed correlation proof → scoped unapplied obligation → current application permit → journal/allocation/workflow/audit commit → verified disposition → guarded clearance**. Proof sealing/binding may commit earlier; money, successful disposition and clearance share the application COMMIT. Financial application can consume its own known source blocker; spending cannot.

| Evidence/lifecycle case | Required transition and clearance predicate |
| --- | --- |
| Genuine pending refund | Retain immutable `refund.pending` admission and neutral AWAITING_CONFIRMATION. A distinct later terminal event/result gets its own source identity and links to that pending history. Do not rewrite immutable operation classification or force a pending row through 0007's confirmed-proof FK. An append-only terminal-followup link can complete tracking when the terminal application commits; pending never becomes a fictitious failed/no-effect refund |
| Confirmed success | Unknown AWAITING_CORRELATION → guarded bind → AWAITING_APPLICATION → CLEARED_APPLICATION only with exact canonical operation/application and full effect/audit/inbox evidence. Confirmed capture follows its new typed proof path, not today's unclassified bypass |
| Confirmed failure/no-effect | Same trusted owner/terminal compatibility checks; CLEARED_NO_EFFECT only with affirmative supported failure plus whole released refund group or operation-specific workflow-only result and no contradictory successful effect. Absence of journal alone is insufficient |
| Contradiction/unknown ownership | BLOCKING_REVIEW or unknown correlation; account barrier until trusted scope, otherwise scoped blocker. Retain original/conflicting identities. No guessed merchant to satisfy scoped exception FKs, no ordinary sealer retry clearing review |
| Duplicate same event | R1 equivalent replay retains original; if processing is needed, verify original application/disposition. No new financial application or financial audit |
| Distinct duplicate event ID | May seal its own fixed proof. Guarded duplicate disposition records exact canonical application/proof/effect references after owner/object/amount/outcome comparison. Keep allocation/hold first provider_event_id and original proof unchanged. It is a verified no-additional-effect acknowledgement, not a second application |
| Late provider response | If matching canonical completion, append source acknowledgement; if merely pending/unknown, preserve truthful status and proven supersession. If contradictory, add review/blocker. Source arrival after completion cannot mutate old financial evidence |
| Worker interruption/reconciliation needed | RETRY/DEAD/ACCOUNTING_EXCEPTION/expired lease leaves obligation/barrier intact. Recovery revalidates claim and proof. A reviewed effect/no-effect resolution is explicit; status/note/elapsed time cannot clear |

### Exact clearance requirements

Extend the R0 resolution model with typed canonical-application/verified-no-effect/duplicate links. R0's original refund recognizer remains a valid narrow precedent; it cannot recognize a different event ID's duplicate by rewriting allocations to reference the new inbox. R2 resolution must check:

1. Exact source ID, contract/proof kind/revision, provider/account/object and canonical payment/merchant/currency/accepted operation. Reject NULL/wrong operation/wrong cause and stale expected obligation revision.
2. Correct operation family/phase and terminal outcome; all owned allocation/hold/item IDs, exact source-specific lines and complete amount/fee group; correct POSTED journal business reference/status/owner/currency. Unrelated balanced journals, including another refund on the same payment, are invalid.
3. Matching immutable financial audit and final workflow/application facts; zero-journal operations require their explicit zero/failed/duplicate proof and complete operation state. ZERO_EFFECT settlement or zero-funded opening is applied state, not evidence that an unrelated refund had no effect.
4. Claim-conditional source disposition and guarded monotonic revision update atomically with the effect or recognition. Ordinary callers have no direct obligation/resolution/exception mutation path. A replay returns the original resolution only after its immutable identity/effect linkage is verified.
5. Every independent active cause remains visible. Add immutable resolution children for R0.2 `(delivery_id,barrier_key)` and for D02 source obligations, with owned effect/no-effect reference, expected revision, actor/principal/audit and resolution identity. Modify the authoritative reader to exclude only barriers with a **validated committed matching resolution**; do not UPDATE/DELETE immutable barriers or trust existence of an unchecked row.

For a formerly unknown barrier, resolution must cover its original broad account ambiguity with verified ownership/no-effect; a scoped journal alone cannot narrow it. If one delivery implicates multiple accounts/scopes, its complete frozen barrier set must be accounted for; partial reviewed progress must leave uncovered causes blocking. Application of the original event alone does not resolve its later contradictory delivery.

R0 can reblock a previously cleared obligation while preserving its unique first resolution. R2 must not reuse that first resolution to clear a later contradiction or rewrite it. Represent the new cause with its own immutable review/obligation episode and resolution, retain the original completion, and guard current obligation state by the exact cause/revision. A review-resolution history extends the model; changing the first `receipt_obligation_resolutions` row is forbidden.

Exception OPEN→RESOLVED requires an evidence-backed typed resolution whose original source/lot/journal/application provenance matches, plus authorized actor/audit. Existing free-text `resolution_reference` is not sufficient new-policy authority. A note-only reconciliation endpoint stays separate. **Resume is another guarded transaction** checking current epoch, revisions, all account/scoped blockers, OPEN exceptions, eligible history and compatible writer floor. Clearance never silently activates or resumes a scope.
