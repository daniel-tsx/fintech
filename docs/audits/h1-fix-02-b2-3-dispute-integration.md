## Implementation and transaction boundary

[CaptureDisputeAccountingService](../../apps/api/src/disputes/capture-dispute-accounting.service.ts) exposes `applyOpened(tx, inboxId)` and `applyClosed(tx, inboxId)`. It locks and reads the actual STRIPE inbox row rather than accepting a caller-constructed financial event. The caller owns commit/rollback. Verified receipt/signature remains the existing receiver's responsibility; fixture inbox rows are explicit local evidence, not live signature proof.

The transaction commits case state, frozen case/lot allocations, original funded hold or close journal, adjustment effects, payment workflow, audit and inbox disposition together. A journal/effect failure aborts all these writes. The separately committed original inbox remains available for whole-transaction retry. Existing CAPTURE journals and provider references are not rewritten.

The service resolves merchant/payment/currency from an existing payment and revalidates it under the payment lock. Dispute object ID must be `dp_...` and equal the normalized provider transaction reference. Amount must be a positive safe integer in the payment currency. Reuse of a dispute object must match its original owner and amount. Selected/frozen captures must establish one known PaymentIntent. A supplied event PaymentIntent and any known trusted capture-mirror PaymentIntent must agree independently. When the event omits PaymentIntent, a matching charge and matching command mirrors for all selected captures can establish the relationship. Only STRIPE/CAPTURE mirrors with the capture's stable command key qualify; owner, amount and provider reference are also checked. Unrelated mirrors cannot authorize an effect. No mirror is written or network call made inside these locks.

## Principal attribution and funded holds

The existing FIFO capacity helper is reused for dispute principal selection: financial capture timestamp at exact microsecond precision, then capture-attempt ID. Each lot subtracts confirmed refunds, outstanding reservations, active/planned dispute principal and confirmed losses from original gross. A unique dispute/lot row freezes the selection. Replay reads that row, so later lots cannot retarget a dispute.

For each selected lot, original net and confirmed refund/loss evidence determine signed surviving entitlement E. Opening funds `min(disputed gross, max(E - existing holds, 0))`. Funding cannot borrow another payment's pending contribution, or another lot's entitlement. Opening immutable `funded_hold` / `unfunded_exposure` records describe initial funding; current funded liability is initial funding plus append-only hold deltas. Current unfunded exposure is gross less current funding, not the unchanged initial exposure field.

| Financial boundary | Exact effect; omit zero lines |
| --- | --- |
| Open, unsettled lot | D own MERCHANT_PENDING / C DISPUTE_CLEARING for funded amount; no asset movement |
| Open, finalized lot | D MERCHANT_AVAILABLE / C DISPUTE_CLEARING; released funds may already have been paid out, permitting explained available debt |
| Win, currently unsettled | D DISPUTE_CLEARING / C MERCHANT_PENDING for remaining funding |
| Win, currently finalized | D DISPUTE_CLEARING / C MERCHANT_AVAILABLE; do not restore the opening account blindly |
| Loss, unsettled | D closing funded hold and own normalized pending where available; D MERCHANT_AVAILABLE for unfunded shortfall; C PSP_CLEARING for gross |
| Loss, finalized | D funded hold plus MERCHANT_AVAILABLE shortfall; C PLATFORM_CASH for gross |

Mixed cases combine those capture-owned legs in one immutable case journal. Original capture fees are retained on loss. Gross10000/net9700 opens hold9700/exposure300; confirmed loss charges available300, never negative pending. A zero-funded opening or win records applied case/allocation/workflow evidence without an empty journal. Loss always has positive gross asset and liability/debt legs.

## Multiple cases and shared hold reductions

[The narrow hold helper](../../apps/api/src/ledger/dispute-hold-adjustment.ts) is shared by the two dormant paths. A confirmed disjoint refund or loss can reduce positive entitlement supporting other OPEN cases. Recalculate surviving holds in stable case order `(opened_at, dispute ID, allocation ID)`, excluding the case being closed. Preserve existing funding up to remaining entitlement; this helper only reduces existing holds, never silently increases them or replaces original journal evidence.

Each reduction posts D DISPUTE_CLEARING / C the lot's current pending or available source **before** the cause's refund/loss journal. It appends one effect with allocation/lot, cause refund/dispute, original allocation (and its opening journal), original inbox, signed delta and adjustment journal. `(allocation_id, effect_key)` is unique; the key is `refund:<cause UUID>` or `dispute:<cause UUID>`. The persisted effect UUID is its journal business reference. Whole-transaction rollback can discard a new UUID; successful cause replay cannot create another effect. Existing hold rows/journals remain immutable.

The merchant debit uses normalized current contribution after reductions, rather than blindly charging an old unfunded estimate. Two gross5000 cases on gross10000/net9700 initially fund5000 and4700. Losing the second releases300 from the first hold into pending and consumes it in the loss debit: remaining hold4700, pending0, available0, PSP5000. There is no phantom300 debt. Losing the final gross5000 instead leaves explained available debt300, with fee retained.

B2.2's prior intentional refusal of disjoint refunds requiring hold reductions is replaced only in the dormant service. Disputed payments may request/apply a disjoint refund after verified history/capacity admission. Refund confirmation preserves DISPUTED while another case remains OPEN. Closing one case preserves DISPUTED while another remains OPEN; closing the last derives CAPTURED/PARTIALLY_REFUNDED/REFUNDED from the locked financial totals. CAPTURE_PENDING and other unsupported combined workflow states retain an accounting exception with the F05/F06 dependency instead of overwriting independent capture evidence. Legacy state-machine/runtime behavior remains unchanged.

## Exceptions, ordering and replay

Ambiguous ownership/amount/provider relation, unavailable disjoint capacity, incomplete legacy allocations, incoherent parent/allocation outcome, existing unapplied close journal or contradictory terminal evidence commits one OPEN accounting exception plus ACCOUNTING_EXCEPTION disposition. The original event, provider references, conflicting refund/dispute allocation IDs and capture references are retained; known capture mirrors are included in provenance. No guessed financial journal or reservation release is committed. Exception/lot links reuse the existing scoped structures and the scope becomes REVIEW_REQUIRED. This blocks new-policy finalization/admission; it does not quarantine pooled funds in current legacy payout runtime.

An ordinary financial rejection commits its exception in the caller transaction. An operational abort rolls that transaction's exception/disposition back too. Tests then retry the separately persisted original inbox and commit one exception. No independent-commit claim is made for an aborted transaction.

After B2.3.1, a close without its opening validates normalized identity, amount/currency/outcome and the known capture/mirror provider relationship before throwing RetryableWebhookError, ahead of financial-history and payment-state admission. It fabricates no case or hold. An existing case still validates frozen allocations, journals and terminal outcomes; actual financial application still checks history and workflow state. The future dispatcher must retain the existing eight-attempt/backoff/DEAD process; this run does not register the service or implement live retry routing. Once the opening prerequisite arrives, the same close evidence can apply. Unsupported or conflicting outcomes are retained for accounting review. Valid duplicate open/close creates no additional journal/audit; repeated open after a coherent close acknowledges old opening evidence without reopening. Identity and coherent applied journal/allocation state are checked before replay guards.
