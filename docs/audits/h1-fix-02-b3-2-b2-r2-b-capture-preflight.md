## 2. Current capture sequence

1. `PaymentsService.capture` uses API idempotency scoped to merchant/operation/key. It locks the payment, checks remaining authorization, creates an independent CAPTURE attempt, sets `CAPTURE_PENDING`, and commits outbox/audit/stored `202` response together. The outbox carries `capture:<attempt UUID>`, exact requested amount/currency, known PI and `finalCapture`. It is the provider key, distinct from the client's API key.
2. Relay publishes the stored envelope through RabbitMQ. Consumer invokes the live handler; ACK follows handler completion. Neither publication nor ACK proves a financial effect.
3. `StripePaymentProvider.capture` calls `POST /v1/payment_intents/<PI>/capture` with explicit `amount_to_capture`, `final_capture`, metadata and the unchanged provider key. It returns PI/Charge/status plus `livemode`, losing actual provider amounts and response bytes at the port.
4. Live command bookkeeping upserts the mutable mirror with **input** amount/currency, then conditionally moves a PENDING attempt to PROCESSING. This does not post a capture. The separate dormant D02 producer instead validates frozen authority, commits an execution before the call, captures each HTTP exchange and publishes immutable source/admission records. It is not wired into that live handler.
5. Legacy signed ingress normalizes the event. For PI success, normalized `amount` is metadata `captureAmount`; for `requires_capture`/`amount_capturable_updated`, metadata selects capture versus authorization. Original PI aggregate fields, Event request causation and previous attributes are not part of the normalized capture amount contract.
6. R1 separately retains verified raw bytes, normalized v1 payload, account, signature and verifier version atomically with admission. PI receipts are currently `provider.unclassified`; they block unknown ownership. R1's correlator returns NOT_SEALABLE for them. A retained signed receipt is not an owned capture proof.
7. Live business correlation prefers payload IDs, otherwise the latest matching mirror. Capture success locks scope before mirror mutation, then payment NO KEY UPDATE and CAPTURE attempt. It validates normalized amount/currency, skips an already SUCCEEDED attempt, rejects a pre-existing journal for an incomplete attempt, computes fees, posts the journal, marks attempt/payment, inserts one original journal-backed lot, audits, and returns. The processor then marks the inbox PROCESSED in its transaction.
8. Current failure can overwrite a successful attempt; processor failure updates lack a claim-generation condition. R2 must not reuse either behavior as proof of terminal finality. Existing live flow remains untouched by this report.

The intended R2 flow inserts **immutable pre-lot proof and guarded binding** between retained R1/D02 sources and financial application. It does not route the current normalizer directly to new accounting.

### 4.2 Builder, shared reader and binding

Provide restricted SQL entry points conceptually named `seal_payment_operation_evidence`, `load_effective_payment_operation_evidence` and `bind_payment_operation_obligation`. The sealer accepts source **selectors**, never authoritative merchant/amount JSON. A single SQL facts routine parses raw receipt and D02 bytes/parameters, applies §5/§7, verifies prospective authority, and returns the typed projection. The sealer persists that projection; the reader revalidates its source fingerprint/lineage and returns that same projection. Both application preparation and immediate/deferred capture validators use this reader. TypeScript consumes its amount and plan; it does not independently interpret PI totals.

Sealing needs no successful CAPTURE status, new capture journal or lot, and no canonical application. It may commit with the accepted attempt PENDING/PROCESSING, zero journals/lots and a still-blocking receipt. Existing authorization provenance is a predecessor source, not the future capture effect. Conversely 0004's lot validator may require the successful attempt and sealed journal **after** those are created in the application transaction. These are separate validations; neither authorizes proof by its own effect.

Sealing and binding each own a fresh READ COMMITTED transaction: private inbox → account UPDATE → canonical merchant/currency advisory → scope → payment NO KEY UPDATE → touched attempts in UUID order → immutable reads. Revalidate tentative ownership under locks. No invocation after a financial suffix or account-SHARE-to-UPDATE upgrade. Proof-only commit leaves unknown admission intact; bind-only failure cannot lose its blocker. Binding advances guarded revisions and transfers only this exact receipt to scoped AWAITING_APPLICATION. It does not acknowledge money or discharge D02.

## 5. Supported provider amount interpretations

### 5.1 What Stripe and the installed adapter actually provide

The capture request supplies `amount_to_capture`; `final_capture=false` retains the remainder only for supported multicapture. The response is a PaymentIntent, not a separate per-capture object. [Stripe capture API](https://docs.stripe.com/api/payment_intents/capture).

The multicapture documentation illustrates 700 then 200 captured on one 1000 authorization: cumulative received becomes 900; final capturable becomes zero because the remainder is released. It documents capture updates and explains that final Charge `captured` can also reflect authorization release. Those are not independent capture-operation amounts. [Stripe multicapture](https://docs.stripe.com/payments/multicapture?platform=web&ui=elements).

Event request information identifies the triggering API request; local SDK types expose nullable request ID/key. The Event's own API version determines its object shape. These fields survive in R1 raw bytes even though the current normalizer omits them. Require their supported form; do not assume they are present on automatic events. [Stripe Event object](https://docs.stripe.com/api/events/object).

The current adapter neither expands a Charge nor retrieves per-capture balance transactions, and authorization does not explicitly request multicapture availability. Its partial-capture command uses `final_capture=false`. A normal final partial capture is valid Stripe behavior, but current `PaymentsService.capture` does **not** emit that command when amount is less than remaining. Do not silently rewrite accepted `finalCapture` to obtain a supported outcome. [Stripe manual capture](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method).

### 5.2 Exact first-capture predicate

`STRIPE_FIRST_CAPTURE_V1` is deliberately stricter than delivery deduplication. All predicates must hold:

1. **Prospective authority:** an accepted CAPTURE attempt/outbox/key, exact immutable owner/currency/policy/epoch, amount `A > 0`, request-target PI and a genuine same-outbox COMMAND_RESULT execution/source. Validate actual SQL-decoded form `amount_to_capture=A` and actual `final_capture` against the accepted payload, including the adapter's default only when the accepted optional field is absent. D02 currently checks amount but does not establish this final-capture interpretation for B1.
2. **Owned zero baseline:** a complete genuine AUTHORIZE COMMAND_RESULT for this payment/account establishes that PI as manual-card authorization, `amount_received=0`, `status=requires_capture`, amount/currency and positive capturable authorization `H`. It identifies the same Charge where present. Require no prior distinct capture proof/application, historical capture journal/lot, unexplained captured aggregate or conflicting command-result for this PI. Same-key redeliveries of this capture are not distinct operations. A known later pending attempt is not by itself a historical capture; its confirmed/unresolved sources still enter admission checks.
3. **Direct response:** COMPLETE 2xx capture response, expected PI/object/account/mode/currency, actual `amount_received=A`, matching Charge and valid integer fields. For final capture require `status=succeeded` and `amount_capturable=0`; for non-final partial require `A < H`, `status=requires_capture` and `amount_capturable=H-A`. `amount` remains the authorization face amount and must agree with the supported baseline. Reject changed authorization, overcapture, tips or other unmodeled amount adjustments.
4. **Signed causation:** admitted original R1 event for the same account/mode/PI/currency and Charge; Event `request.idempotency_key` equals the original `capture:<attempt>` and non-null `request.id` matches an actually retained same-key capture exchange's response `request-id`. The correlated exchange must itself meet the direct-response predicate. A cached retry's different request ID is not presumed equal to the original one. If none matches, refuse until genuine additional evidence exists.
5. **Signed outcome/amount:** for final capture, allow `payment_intent.succeeded` with the same successful PI values; for the first non-final partial, allow `payment_intent.amount_capturable_updated` with the same `requires_capture`, received `A` and remaining `H-A`. In the latter require signed `data.previous_attributes.amount_capturable=H` as corroboration of this first reduction. `requires_capture` alone and an authorization-time capturable event fail. No subtraction of final capturable amounts to determine principal.
6. **Consistency:** metadata is corroboration; any explicit owner/attempt/amount contradiction blocks. Missing metadata is acceptable only when the retained normalization makes no contradictory claim: for example `provider.unsupported` on a final success can be classified from exact raw causal evidence. On a non-final partial, missing capture metadata currently produces normalized `payment.authorized`; that phase/attempt disagreement remains blocked in initial B1 despite otherwise matching raw facts. Do not silently override it or claim universal metadata-free partial support; a future isolated normalization version would need explicit review. Restrict actual request and signed-object API versions to reviewed parsers (initial D02 version above and explicitly tested event versions); unknown shape/version blocks. Parse numeric JSON as exact SQL numeric integers before bigint/range checks, not permissive text casts. Check duplicate financial/identity keys in a duplicate-preserving SQL JSON parse before conversion to jsonb; conversion alone would conceal them. The same facts helper owns that validation for sealing and reading.

**Why this is operation-specific:** `A` is the amount of an authenticated, owned capture request whose actual successful response and signed causative event agree. The independent zero baseline and absence of a prior distinct capture exclude allocating a cumulative amount across attempts. `amount_received=A` is a corroborating equality, not a general rule that cumulative received belongs to whichever metadata attempt is current. The baseline and sources exist before the future lot/application. No capture proof depends on its future effects.

Require `A`, `H` and every decoded monetary field to be nonnegative safe integer minor units, with capture positive and not exceeding authorization. Refuse missing body, partial body, malformed/duplicate ambiguous fields, missing causal key/ID, wrong mode, amount mismatch, unsupported version or competing outcome. Real Stripe may omit a required field or use another event contract; that input remains blocked. Test fixtures establish parser/refusal behavior, not universal availability of these fields on Stripe accounts.
