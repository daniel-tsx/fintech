## 3. Independent attributable-amount assessment

The following is an engineering inference from the proposed conjunction, not an assertion that every Stripe account supplies it. Stripe's [capture API](https://docs.stripe.com/api/payment_intents/capture) defines the requested amount and final-capture behavior; its [multicapture contract](https://docs.stripe.com/payments/multicapture?platform=web&ui=elements) describes cumulative received amounts, remainder release and capture update events. The [Event contract](https://docs.stripe.com/api/events/object) identifies request causation and event rendering version. These support the field interpretation. They do not replace the owned retained sources or prove availability of every required field.

For **every issuable capture proof**, require all of this common witness, as specified in preflight §5.2:

- Exact prospective CAPTURE authority/outbox, attempt, merchant/payment/currency, original provider key, accepted policy/epoch and immutable payload. A genuine COMMAND_RESULT execution and HTTP exchange must belong to that outbox; a lookup cannot substitute.
- SQL decoding of the actual POST path/form/key/account must agree with acceptance, including `amount_to_capture=A` and the final flag. A separate owned AUTHORIZE COMMAND_RESULT establishes this manual-card PI/Charge, currency and authorized/capturable `H`, with received zero. Metadata never supplies that ownership.
- Complete successful capture response and signed original R1 event must agree on account/mode, PI/Charge, face amount, currency, received amount and the supported terminal/capturable state. The event's non-null request key equals the accepted capture key; its request ID equals the response request ID of a retained qualifying same-key exchange. A retry with a different ID cannot be assumed to match.
- `A > 0`, exact integer monetary fields, supported ranges/versions, no unexplained recognized capture, distinct earlier capture or competing ownership/outcome. Refuse malformed/duplicate ambiguous JSON keys before conversion to jsonb hides them. Explicit normalized/metadata contradictions retain review; the normalizer's partial-as-authorization case is excluded.
- Freeze proof version 1, interpretation `STRIPE_FIRST_CAPTURE_V1`, original receipt/source IDs and fingerprints, parsing/sealing provenance and the typed source set. Binding records the exact obligation revision. Event identity is source identity; the financial terminal identity is `(CAPTURE, attempt UUID, TERMINAL, currency)`.

Why the first-capture reasoning works: the request names one accepted operation and amount A; a genuinely successful response reports the same received A; the signed event names that request and agrees on its amount/state. Independent zero authorization provenance and exclusion of distinct captures prevent allocating an accumulated total across operations. This is materially stronger than selecting the latest attempt metadata from a PI snapshot.

Duplicate handling must distinguish **A's own established effect** from a distinct predecessor when re-reading a proof. The preflight's §6.4 replay contract already requires that distinction: A remains the same first capture after its own journal exists or another attempt is merely pending. Dynamic eligibility can block on later conflicting evidence, but cannot change the immutable proof's original principal or reinterpret A as a subsequent capture.

## 4. Pre-lot proof, R0/R1 lifecycle and one SQL interpretation

The proposed companion breaks the dependency in the right place:

```text
accepted command + genuine authorization/capture exchanges + original signed receipt
  -> SQL facts -> immutable operation proof -> guarded obligation binding
  -> later SQL permit/plan -> journal + successful workflow + original lot + application
```

The upper line exists while the CAPTURE attempt is PENDING/PROCESSING and there are **zero capture journals/lots**. The lower line is later B2 work. The existing lot trigger may validate its newly posted journal/successful attempt in that application transaction; the proof must never read those future effects to establish its amount. Negative checks for unrelated prior effects do not require creating this capture's effect.

| Contract property | Review conclusion / implementation acceptance requirement already present in the preflight |
| --- | --- |
| Authenticated ownership | R1 attests SDK-verified original bytes/configured account; D02 attests real owned transport and prospective command authority. SQL independently joins and decodes them. SQL is not being claimed to authenticate TLS or recompute HMAC. A metadata-selected mirror cannot fill a missing link. |
| Immutable identity/provenance | Typed owner FKs include attempt/payment/merchant/currency and exact authority/source lineage. Freeze bytes/digests, verifier/normalizer/parser versions, event API version and actual exchange identity. Do not make PI/Charge unique per capture or reconstruct raw evidence from JSON. |

No TypeScript-derived authoritative amount or independently trusted parsed snapshot. |

## 8. Human decision brief

- **Provable example:** a zero-received USD 100.00 authorization has an owned accepted USD 40.00 capture. The actual request sends 4000 minor units under that attempt's key; its complete response and signed causative first capture update both show 4000 received and 6000 remaining, with the same PI/Charge/account/currency. The principal is USD 40.00 even though the PI face amount is USD 100.00.
- **Ambiguous example:** after USD 40.00 was captured, an event names another attempt and the PI says USD 100.00 received. That total alone does not identify this operation's contribution. B1 refuses it; it does not credit USD 100.00 or guess USD 60.00 by subtracting today's local state.
- **No circular proof:** accepted command, authorization response, capture response and signed event already exist before the local capture journal/lot. SQL seals that evidence first; later accounting must consume it. The lot then proves the original posted effect, not its own authorization.
- **What B1 builds:** durable, versioned evidence and classification/binding, with a shared SQL interpretation and refusal tests. It creates no journal, lot, financial application, terminal no-effect disposition or live route.
- **Deliberate exclusions:** later shared-PI captures; aggregate/metadata/mirror-only evidence; missing causal request/key/complete response; unknown API shapes; contradictory phase/ownership; unsupported historical sources; automatic negative-outcome inference; captured-void/remainder-release ambiguity. Current external multicapture availability and actual required webhook fields still need later test-mode verification.

B2's authorization prerequisite may require the substage adjustment above. The human still decides when to authorize implementation and later operational account/mode/credentials, H04 triage ownership/deadline, D03 cohort/fence and installation/activation.
