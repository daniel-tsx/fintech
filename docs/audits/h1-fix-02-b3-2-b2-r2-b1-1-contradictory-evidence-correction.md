## 3. Authoritative evidence-set interpretation

### Historical authorization responses

The additional SQL loop reads **every other RETURNED_OBJECT / COMMAND_RESULT for `auth.outbox_id`**, checks each through `checked_payment_command_source`, then compares object/PI/Charge, mode, currency, status, manual capture method, face amount, received amount and capturable capacity with the independently owned selected authorization. No timestamp, latest row or LIMIT1 selects away a competing source. Complete actual request/body/version/account/key checks and immutable accepted ownership remain required.

Matching command-result retries are equivalent when these interpreted facts agree. Additional nonfinancial response fields do not invent a contradiction; explicit owner conflicts still fail D02's checked-source/coarse blocking checks. The additional loop also validates metadata shape and explicit merchant/payment/authorization-attempt/currency contradictions against the accepted authorization. Metadata can disqualify evidence but cannot establish ownership or principal. The original source UUIDs, raw bytes and fingerprints are never overwritten or merged. The capture/void command's existing detailed response/lookup restrictions remain unchanged.

An authorization **PROVIDER_LOOKUP** is current-state evidence, not another historical result of the original authorization POST. A legitimate owned lookup after the first partial capture can report received4000/capturable6000 while the original authorization remains received0/capturable10000. The new baseline loop excludes that lookup; existing D02 owner/conflict blockers still apply, and a lookup cannot fill a COMMAND_RESULT selector. No provider outcome precedence or negative-outcome inference is introduced.

### Authenticated signed evidence

SQL examines retained originals and independently verified later deliveries in the configured provider/account, then relates each to the selected accepted operation or its authorization using **the accepted idempotency key or an actual retained response request ID**. A same-PI or metadata/amount match alone is insufficient. Once either causal identifier relates a source, both the exact accepted key and an attested same-command returned-object request ID must agree. A conflicting identifier cannot route a source away from checking.

Each related source must agree with the corresponding command response, not indiscriminately with the later capture: historical authorization events compare with the zero baseline; capture and void events compare with their own response/phase. SQL checks supported API version, configured account/mode, PI/Charge, integer amount/received/capturable fields, outcome/type, applicable cancellation/final/previous-capacity facts, explicit metadata contradictions and normalized phase/owner/principal. A retry may have a different response request ID only when that ID belongs to another retained same-command result which the response checks also validate.

Distinct event IDs, delivery times and harmless additional fields do not create financial identity or defeat equivalence. A coherent event remains a separate original with its own proof/obligation; it does not get acknowledged by the first proof. Different accepted pending operations, including ones sharing the PI, retain their own unresolved obligations and are not folded into the first capture. Subsequent capture proof issuance remains unsupported.

Related signed failure retains the existing reordered-failure refusal, without issuing confirmed failure/no-effect evidence. Related R0.2 CONFLICT deliveries remain blocking, including a later contradiction on another coherent original. Original and later-delivery bytes, reviews and barriers are preserved. Duplicate/ambiguous JSON is still checked before jsonb interpretation; ambiguous account evidence fails closed rather than gaining ownership from metadata.
