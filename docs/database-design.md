# Database design

Status: current. The executable schema is in `apps/api/src/database/schema.ts`; the checked-in SQL migration is authoritative for constraints and triggers.

## Aggregate tables

- `merchants`, `users`, `api_keys`, `customers`
- `payments`, `payment_attempts`, `provider_transactions`
- `refunds`, `disputes`, `settlements`, `settlement_items`, `payouts`
- `ledger_accounts`, `ledger_transactions`, `ledger_entries`
- `webhook_events`, `idempotency_keys`, `outbox_events`
- `reconciliation_runs`, `reconciliation_issues`, `audit_logs`

`provider_transactions` stores local Stripe command references and last-known state. It is a cache/mirror, not the provider source of truth. Multiple command rows may reference the same PaymentIntent; provider idempotency keys, not provider object IDs, are unique per command.

Records use UUIDs; provider object references use provider-issued strings. Money columns use `bigint` minor units; the payment currency has a three-letter check. The deferred trigger checks journal/entry currency consistency. Foreign keys preserve record references, but are generally not composite tenant-ownership constraints; services must validate merchant ownership explicitly.

## Database-enforced invariants

- One idempotency row per `(merchant_id, operation, key)` and request hash comparison on replay.
- One webhook inbox row per `(provider, provider_event_id)`.
- One provider operation per provider idempotency key.
- Captured/refunded amounts cannot be negative and cannot exceed the payment amount/captured amount.
- Ledger entries are positive, one-sided debit or credit rows.
- Deferred constraint trigger rejects posted ledger transactions whose debits and credits differ, have fewer than two entries, or mix currencies.
- Entry INSERT requires a DRAFT parent and updates that parent without changing its status. This serializes entry construction against posting and invalidates stale repeatable-read posting snapshots. [Migration 0002](../apps/api/drizzle/0002_seal_posted_ledger.sql) also refuses installation over existing invalid posted journals and blocks ledger-table TRUNCATE.
- Triggers reject updates/deletes of posted ledger transactions, ledger entries and audit logs. A separate trigger protects webhook provider/event/type/signature/payload fields on updates.
- Each capture attempt can appear in only one settlement item. Payout journals use unique ledger business references.

Balance snapshots are deliberately not the source of truth. Current balances are calculated from ledger accounts and entries. A production system may maintain an asynchronously verified projection for scale.

Ledger sealing, deferred balance checks, immutable-row triggers, functional account uniqueness and hand-authored foreign keys are SQL guarantees beyond the Drizzle table definitions. Keep the checked-in forward migrations; generating a table schema does not reproduce these triggers. The [F02 fix record](audits/h1-fix-01-posted-ledger-immutability.md) owns the change's migration and verification evidence.

[Migration 0003](../apps/api/drizzle/0003_pin_ledger_function_context.sql) replaces the balance function in place with explicit `public` table/type references and pins all four ledger trigger functions to `pg_catalog, pg_temp` with `SECURITY INVOKER`. Ownership, execution grants and trigger identities are preserved. Its transactional preflight again refuses invalid POSTED history. Drain financial writers before applying: header/entry `SHARE ROW EXCLUSIVE` locks block writes during the scan and function replacement; ordinary reads remain possible.

## Installed B1 foundation, dormant at runtime

Runtime refund/dispute/settlement dispatch does not consume allocations; the separate B2 services do so only through isolated dormant tests. The existing gate permits only `FOUNDATION_ONLY` or `REVIEW_REQUIRED`; ACTIVE remains structurally unavailable. B2.1 requires 0000–0004 and introduces no migration or historical backfill.

Composite ownership keys connect new lots, intentions, exceptions and journals by payment/merchant/currency. Deferred checks enforce whole-intent allocation, aggregate principal/funding capacity and journal amounts; terminal allocations/effects and original capture values are immutable. Persistent SQL references are qualified and all eight new functions use invoker privileges with `pg_catalog, pg_temp`. This does not repair ownership constraints in unrelated legacy tables.

Nullable settlement/item columns distinguish policy, estimates, revisions, final asset transfer/release, restricted hold, final journal and explicit ZERO_EFFECT evidence. Legacy gross/fee/net fields retain their meanings; legacy writers leave all new fields null. Historical migrations and F02 functions/triggers are preserved.

The live `capture_accounting_legacy_inventory` and `capture_accounting_orphan_inventory` views support inspection, not activation. Installation backfills only canonical, unadjusted, unsettled original captures, with legacy eligibility left null. Adjusted/settled/invalid captures and scoped orphan journals create review exceptions without fabricated allocations. Unscoped CAPTURE evidence makes migration 0004 refuse atomically. Drain writers before applying: the transactional maintenance locks and added unique/FK constraints can block writes and reads. The [B1 record](audits/h1-fix-02-b1-allocation-foundation.md) owns migration tests, recovery precautions and B2 cutover prerequisites.

Fresh 0000–0005 installation, repeated migrator no-op and populated 0004 upgrade are tested. Keep the additive label/evidence on application rollback. [B2.2](audits/h1-fix-02-b2-2-refund-integration.md) uses it only through the separate dormant refund path; live runtime routing is unchanged.

[B2.3](audits/h1-fix-02-b2-3-dispute-integration.md) reuses existing dispute allocations, append-only hold effects and exceptions without schema changes. Original funded hold/exposure stay immutable; current funding adds effect deltas. [B2.4](audits/h1-fix-02-b2-4-settlement-integration.md) reuses 0004 settlement/item estimates, originals, final amounts/revisions/holds/results/journal/timestamps and lot state, without a new migration. Later effects advance lot revisions without rewriting saved finalization; replay validates that historical snapshot. Legacy batches and uncertain legacy lots remain review-only; no historical schema/data rewrite or activation occurs.

## Trusted evidence foundation: financial application still closed

[Migration 0006](../apps/api/drizzle/0006_trusted_financial_evidence.sql) adds configured evidence accounts, original signed receipt snapshots, immutable command-result/lookup observations, provider-object ownership, sealed webhook proofs and append-only unscoped reviews. The original inbox UUID remains durable identity. PostgreSQL validates attestation lineage and raw/normalized/owned financial facts; trusted publishers perform SDK verification outside database locks. The current receiver/consumer does not publish these structures. Historical JSON/signatures are not reconstructed into authenticated receipts.

`seal_financial_correlation` and `load_effective_financial_evidence` share one checked SQL interpretation. Refund identity uses accepted commands/keys and frozen original captures; disputes use uniquely owned capture evidence. PI matching or mutable mirrors alone are insufficient. Object ownership is unique per provider/account/kind/external ID, while captures may share a PI. Proof revision1 is immutable; frozen capture amounts are decimal strings in provenance JSON. Receipt/proof/binding/observation/review mutations and TRUNCATE are rejected.

Refund/dispute/hold rows have future owned composite proof references, but CHECK/NOT NULL constraints currently force version0 and NULL references. `assert_financial_evidence_runtime_ready()` refuses every new-contract application; account enforcement is immutable UNINSTALLED and ACTIVE remains unavailable. Version0 means old format, including legitimate new legacy/test writes; it does not certify historical or activation eligibility. Both original 0004 allocation validators and all F02 functions remain unchanged. B.2 must install their shared-reader adapters, protected historical-era/default1 guards and full deferred financial/workflow/audit/inbox linkage before any gate opens. A schema flag or successful proof does not authorize financial application.

The B.1 sealer owns inbox→account intake UPDATE→advisory/scope→parent/lot locks. It requires a fresh correlation transaction before shared-intake or later financial locks; future admitted application uses the reader after its own authority. B.2 cannot invoke this self-locking routine after intake SHARE/A/S and assume lock compatibility.

Installation needs a privileged migration identity able to create a narrowly restricted per-database non-login function owner. The sealer/header guard pin their path; the owner has required evidence reads and limited lock/INSERT privileges but no ledger writes. Other new routines remain invoker-based; PUBLIC execution/table defaults are revoked. Live publisher/worker grants, credential separation and worker fencing are not implemented here. Existing status-only inbox writers need no new receipt SELECT permission.

Receipt publication advances the private inbox's row version with a same-value updated_at write, preserving its exact timestamp/evidence. A stale repeatable-read header writer then aborts instead of missing receipt protection in an old snapshot. Current triggers add no timestamp/audit side effect; the intentional parent write and its ordinary PostgreSQL regression are documented in the checkpoint.

Drain writers for installation: explicit ACCESS EXCLUSIVE locks cover inbox and three allocation/effect tables; additive constraints/indexes validate under the transaction, with a 10-second lock wait bound. Late failure rolls back the schema/function/role additions; no historical monetary evidence is rewritten or trusted through migration. See the [B.1 implementation and verification record](audits/h1-fix-02-b3-2-b1-trusted-evidence-schema.md) for executed PostgreSQL18.6 tests, role boundaries, historical compatibility and precise B.2 dependencies.

## Receipt admission foundation: runtime still dormant

[Migration 0007](../apps/api/drizzle/0007_receipt_admission_foundation.sql) adds immutable receipt-contract enrollment and completion evidence, a mutable one-per-inbox obligation, a provider/account intake revision and the existing scope's guarded evidence revision. Known ownership uses the fixed B.1 proof tuple. Unknown ownership creates an account-specific barrier; guarded mapping replaces it with a scoped unapplied blocker atomically. Genuine pending refunds retain nonblocking AWAITING_CONFIRMATION under Option A. Immutable receipts/proofs are not overwritten by lifecycle changes, and legacy inbox dispositions cannot clear obligations.

The restricted atomic SQL publisher inserts receipt plus enrollment/obligation; a deferred constraint rejects a relevant enrollment without its mandatory blocker or a false unrelated classification. No runtime login receives publication/management rights, and the real SDK/HTTP publisher is not implemented. Existing B.1 receipts remain unadmitted unless explicitly enrolled through the new contract; installation performs no backfill or historical promotion. Both existing financial proof gates and the absence of ACTIVE remain unchanged.

R0.1 classifies contradictions before granting pending/nonfinancial exemptions. Contradictory normalized outcomes, amounts, currencies, provider identities or explicit owners retain the original receipt plus an immutable CONTRADICTORY review and an unknown-owner BLOCKING_REVIEW obligation. The account barrier and evidence revision commit atomically; no owner is guessed. Confirmed outcomes reuse B.1's financial-fact validator. Only genuine pending with version1 unsupported/null normalization remains Option A neutral. Deferred checks require the retained contradiction review and refuse a nonblocking disposition. The admission owner gains append-only review INSERT, without review mutation or ledger writes; ordinary publisher/worker grants remain absent.

The first database completion recognizers acknowledge an already applied exact refund journal/allocation/audit or confirmed failure with released reservations and audit. They post no money, do not upgrade version0 history and do not authorize a new financial application. Other completion forms and full financial/disposition linkage remain R2 gates. The isolated receipt reader checks both revisions, blockers and OPEN exceptions under account/advisory/scope locks; it is not a financial permit or a complete reconciliation certificate. Legacy writers do not yet participate in these revisions.

Admission uses private inbox → chosen account intake mode → advisory/scope NO KEY UPDATE; unknown mapping uses exclusive intake without a SHARE upgrade. A separate restricted non-login owner manages only admission storage/revision columns, with no ledger writes or public execution. Explicit scope-table ACCESS EXCLUSIVE and referenced-table DDL locks require a drained transactional install. See the [R0 record](audits/h1-fix-02-b3-2-b2-r0-admission-foundation.md) for lifecycle, lock composition, migration rollback, capability tests and the remaining R1/R2 integration gates.

## Later verified deliveries: dormant conflict barriers

[Migration 0008](../apps/api/drizzle/0008_conflicting_receipt_deliveries.sql) adds immutable `receipt_delivery_attempts` and `receipt_delivery_barriers`, independent of the original receipt's obligation. A later verified financial contradiction can therefore block the staged admission reader even when the original was nonfinancial. Original receipt bytes, enrollment, proof and journals remain unchanged. Exact repeated attempts return the same row; equivalent signed JSON/account/normalization with refreshed signature or transport headers retains another witness without a new barrier. SQL requires a restricted publisher capability; the future R1 adapter must independently verify each delivery with the SDK and server-configured account context before invoking it.

The publisher atomically retains later bytes/provenance, creates its immutable review and exact derived barrier set, and advances existing R0 revisions. Deferred triggers rederive classification and reject missing/extra barriers at commit. Canonical validated B.1 proof supplies a known merchant/currency; otherwise each financially implicated configured account receives its own unknown-owner barrier. Unknown proof selection stays frozen for that witness even if correlation later becomes available. The existing reader preserves its locks and predicates while additionally checking account barriers and pooled merchant/currency barriers. Legacy runtime readers/writers remain unchanged, so this is not live settlement or payout quarantine.

New evidence/barriers reject UPDATE, DELETE and TRUNCATE; no conflict-clearance operation exists. Original obligation resolution, notes and inbox status cannot clear them. A later reviewed R2 migration must provide matching trusted reconciliation/no-effect, actor/audit, immutable resolution history and guarded revision changes before recovery can succeed. The admission owner gains only SELECT/INSERT on the two new tables; no runtime login grant, credential, financial write right or activation gate changes. Installation is transactional with a 10-second lock wait bound: drain receipt writers for referenced-table FK DDL locks and function replacement; no historical scan/backfill or data repair occurs. Fresh/populated upgrade and rollback evidence is in the [R0.2 record](audits/h1-fix-02-b3-2-b2-r0-2-conflicting-delivery.md).

[R1's isolated adapter](audits/h1-fix-02-b3-2-b2-r1-signed-receipt-integration.md) now consumes these installed contracts without a migration or live registration. A newly inserted inbox commits with its receipt/enrollment/required obligation; existing enrolled identities use0008 only after independent SDK verification. Bare legacy inboxes or B.1 receipts remain review-only. Correlation selects only existing same-account immutable refund command observations, uses the checked B.1 sealer for canonical ownership, then binds in a separate transaction. Missing provenance records an unresolved review, not a fabricated observation/proof. No financial row, historical evidence, scope gate, SQL function/grant or migration0000–0008 changes. Earlier references to an unimplemented publisher mean the live/deployed publisher; signed local HTTP and restricted-login composition are now tested in isolation.
